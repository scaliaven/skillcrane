[ skillcrane ]

Gamepad teleoperation for MuJoCo manipulation that records LeRobot demonstrations — natively, or on robosuite, RoboCasa, Meta-World, Fetch and LIBERO.

MuJoCo 3.12 Python 3.11+ macOS / Apple Silicon 100 Hz control 5 benchmarks 230 tests passing

What it became

It started as a game. The game turned out to be the data collector.

A skill crane is the trade name for an arcade claw machine, and that is what the first version was: a scoring loop. Grab the orange cube, drop it in the green zone, beat the clock. Building that well meant solving the hard part of a teleoperation rig anyway — an arm that tracks your hand smoothly enough that a human can actually do fine manipulation with it.

Once that worked, every round played was already a demonstration. So the same rig now logs each control tick as an imitation-learning episode. The game is the interface; the dataset is the output.

Phase 1 — where it started

Manipulation game

Gamepad teleop, camera-relative sticks, pick-and-place scoring with a timer and a streak counter. Score requires the cube settled, in the zone, and the gripper released.

Phase 2 — where it is

Manipulation in sim + data collection

Same arm, same physics, now instrumented. --record writes state, action and a rendered frame every tick in LeRobot format — the shape an ACT policy trains on.

Run it

Seven commands

# play
python main.py

# scripted pick-and-place, no window, exits 0 on a score
python main.py --headless

# collect demonstrations as a LeRobot dataset
python main.py --record runs/

# score a policy over 12 seeds, or replay a recorded episode back
python main.py --eval 12
python main.py --eval 1 --policy replay:runs/:0

# drive an existing benchmark with the same rig
python main.py --list-envs
python main.py --env robosuite:Lift

# find your 8BitDo's axis and button indices
python gamepad_probe.py

# 230 tests, no display and no gamepad needed
python -m pytest

The part that was actually hard

Three lag sources, one number

The tracking budget was 10 mm. The first working version sat at 65 mm on a 0.3 m/s sweep, and the error scaled linearly with speed — the signature of a lag, not a tuning wobble. It never reached 10 mm even at a tenth of full stick, so it had to be fixed rather than measured around.

65.0 8.2 mm peak error  /  0.3 m / s sweep
Source Why it lags Fix Was
IK command A proportional chase trails a moving goal by v/kp, forever velocity feedforward 8.4 mm
Position servo Follows its own command by kv·q̇/kp kp 800→2500, kv 60→40 21.4 mm
DLS damping Damping is undershoot — the solver under-delivers the twist lam 0.10→0.04 —
Gravity droop Static sag against a position servo; speed-independent floor left in place 1.4 mm

The actuators peak at 13 N of a 200 N forcerange, so the stiffer gains buy tracking without saturating anything. Tuning stopped at passes with headroom, not minimised: a stiffer teleop loop reaches 5.6 mm but is a real feel regression.

Data collection

What a round leaves behind

One row per 100 Hz control tick: observation.state is six joint angles plus gripper opening plus cube xyz; action is what the operator actually asked for, not what the joints did; next.reward is 1.0 on the tick that scored. A 90-second round is about 9,000 rows. 

runs/
  data/chunk-000/episode_000000.parquet     observation.state, action, next.reward…
  images/observation.images.scene/
    episode_000000/frame_%06d.png           one rendered frame per tick, per camera
  meta/info.json                            v2.1, fps 100, feature schema
  meta/episodes.jsonl  tasks.jsonl  episodes_stats.jsonl

Each episode’s row in episodes.jsonl carries success and score, because the usual ACT recipe trains on demonstrations that worked and a directory of rounds with no outcome cannot be filtered into one. pyarrow and pillow are imported lazily, so the core keeps three dependencies.

A well-formed dataset can still be untrainable, and nothing else here can see it: --headless --record once logged [0, 0, 0, 0, grip] on every tick of a completed pick-and-place, because the scripted demo moved the Cartesian target directly instead of through the sticks. Every column was present, every shape correct, every frame on disk. The check is to replay the file into the simulator it came from — --policy replay:runs/ reproduces the episode to 1.6e-7 of state over ~700 ticks, and misses when replayed into a different seed, which is what makes the first number worth reading.

Benchmarks

The same rig, pointed at somebody else's tasks

These benchmarks already take the action this project produces — a Cartesian delta plus a gripper bit — so the adapters are a remapping, not a re-implementation. The native arm goes through the same contract, which is what keeps them honest.

Two words, kept apart everywhere: a suite is a benchmark — a different robot, a different wrapper, a different observation width — and a task is one setting inside it. robosuite:Lift names both, and the two are switched by different controls while playing, because they are different moves. The suite ring holds only what is installed, so on a bare checkout it is one entry long and the HUD says suite native 1/1 rather than looking broken.

Three landmines, each found by running it rather than reading about it: mujoco ≥ 3.12 breaks every robosuite-based benchmark (its mujoco-py shim compares a pybind11 enum against a numpy.int32, and the reflected direction started returning False — bisected: fine through 3.11.0, broken at 3.12.0); egl_probe will not build on CMake 4; and importing robosuite sets MUJOCO_GL=cgl, which gymnasium does not recognise, so one benchmark silently breaks another in the same process.

Gripper close signs disagree between benchmark suites and were measured, not assumed — robosuite +1, Meta-World +1, Fetch −1, LIBERO +1. A wrong sign makes a task quietly unsolvable while looking like bad teleop, so a test pins them.

Load-bearing

Findings that look arbitrary and are not

  • Structural links carry no collision. MuJoCo skips its parent–child contact filter for bodies welded to the world, and a fixed base with no joint is world-welded — so the base geom grinds against link 1 and the yaw joint oscillates above 15 rad/s.
  • The IK integrates on a scratch MjData. Feeding measured pose error into a command that position actuators are already chasing closes a loop through the actuator dynamics.
  • The offscreen framebuffer is declared in the MJCF. It defaults to 640×480 and raises rather than downscaling.
  • The Cartesian target is rate-limited. It moves by stick × speed × dt and never jumps, or the arm flings the payload.

All nine are written up in CLAUDE.md, each with the symptom it produces, because every one of them reads like something to tidy away.
